# Phase 1 research — 2026-09-18

> Update after direct source audit: the product is now named **HerThing** and is
> intended as a public, provider-neutral project. Recovery-mode USB enumeration
> is verified as `1b8e:c003`. Mira remains the recommended image foundation.
> Nocturne has the strongest microphone implementation, but its supplemental
> image/API license terms make a wholesale fork unsuitable; see
> [ADR 0001](adr/0001-firmware-foundation.md).

## Executive conclusion

The project is feasible. The microphones are not merely theoretically
accessible: two public projects capture useful PCM audio today. Mira performs
wake detection and general ASR locally on the Car Thing; DeskThing's microphone
package exposes 16 kHz mono, 16-bit audio as WAV-framed chunks. USB Ethernet is
already a supported device/host link, so conversational audio is tiny relative
to available USB bandwidth (256 kbit/s raw at 16 kHz mono S16LE).

Use Mira as the initial hardware/firmware base, but do not adopt its product
architecture wholesale. Mira is optimized as a standalone Spotify appliance
whose voice resolver recognizes a fixed music grammar. This project needs a
host-centric, generic assistant transport. Fork the smallest Mira layers needed
for reliable hardware support, replace its UI, and add a generic bridge.

## Current ecosystem

### Mira — recommended base

Status: very active. The organization repositories were updated in September
2026, and the current public firmware release is 1.2.1.

What it already proves:

- Fully open firmware image builder, Go daemon, React/Vite UI, and voice stack.
- 800x480 Chromium kiosk UI with touchscreen and gesture support.
- Rotary knob, knob press, four presets, back, and power controls.
- Bluetooth PAN tethering and USB Ethernet tethering on Linux/macOS/Windows.
- Spotify observation and remote control through the Connect state protocol,
  with HTTP/WebSocket APIs for the UI.
- Local microphone capture, an openWakeWord-derived `hey_mira` model,
  endpointing, sherpa-onnx Zipformer ASR, and an intent/phonetic resolver.
- Its published architecture reports about 3.4–3.6 seconds for warm
  wake-to-play on the Car Thing's CPU, without GPU inference.

Limits for this goal:

- Its shipped voice flow is a command grammar feeding Spotify actions, not an
  open conversational assistant.
- On-device ASR consumes scarce CPU/RAM and adds latency we can avoid on the
  much stronger host.
- Its UI/API is Spotify-oriented rather than the generic Muse boundary wanted
  here.

Reuse: image/kernel/device support, input handling, microphone/ALSA knowledge,
USB networking, kiosk lifecycle, backlight support, and selected UI patterns.
Adapt: wake/VAD code to emit utterance PCM and events. Replace: command resolver
and primary UI.

### Nocturne

Status: highly active. The monorepo and releases show a rapid 4.1.x release
series in August/September 2026. It is a sophisticated Yocto-based A/B OTA
platform with a Rust device daemon, React 19 kiosk UI, Bluetooth/iAP2, USB link,
and companion/connector software.

Capabilities: complete display/touch/physical controls, Spotify, Bluetooth,
USB connectivity, voice capture, wake controls, OTA, and a mature daemon/UI
protocol. The development image includes Weston, VNC, and debugging tools.

Why not the first base: it is a much larger platform, portions depend on a
separate API and paid companion features, and the architecture/license surface
is less direct for a private generic assistant fork. It is excellent reference
code, especially for its modern Yocto hardware layer, protocol, OTA, and audio
capture improvements. Re-evaluate it if Mira's Buildroot base proves unstable.

Direct source inspection found that its audio implementation captures the full
four-channel PDM array at 48 kHz S32_LE, performs wind-aware mixing,
filtering/decimation, noise suppression and VAD, and produces mono 16 kHz Opus
in 60 ms frames. It is the current technical benchmark. Its image license also
adds mandatory user-facing wording and refers users to a separate API license;
HerThing should not copy this implementation without deliberate license review.

### DeskThing / Thing Labs

Status: active. DeskThing requires Node >=25 for current development and is a
host/server plus Chromium web-client app platform. Thing Labs also maintains
Terbium, thingify.tools, Superbird U-Boot/FIP work, and reconstructed stock UI.

Capabilities: custom web applications; touchscreen and configurable mappings
for knob/buttons; display management; USB host communication; Spotify and host
media integration. The separate `@deskthing/microphone` package installs an
on-device daemon and exposes raw audio packets to JavaScript (documented default
16 kHz, mono, 2 bytes/sample, one-second WAV chunks).

Why not the first full base: it brings a general plugin/desktop framework and
Electron management surface that this single-purpose appliance does not need.
Its microphone package is young and lightly adopted. It remains valuable as a
fallback/reference implementation for raw audio streaming and input mapping.

### Thing Labs tooling

- **Terbium:** browser/WebUSB Amlogic flashing workflow and firmware catalog.
- **FlashThing:** newer Rust library/CLI/Node/WASM flasher supporting Amlogic
  vendor burn mode and fastboot with the Terbium archive metadata format.
- **superbird-tool / bulkcmd:** older low-level boot, dump, and root tooling.
- **thingify.tools:** discoverable firmware/tool distribution.

Prefer FlashThing CLI for scripted, inspectable development/recovery when its
support matches the chosen image; keep Terbium as the documented interactive
fallback. Never begin by blindly flashing the catalog default.

### Older stock-derived projects

The reconstructed stock webapp, stock root exploit/toolkits, and temporary
unbrick images remain useful documentation and recovery aids. They are not good
foundations for a new assistant: stock services were tied to Spotify's retired
backend/app flow, while the modern Mira and Nocturne stacks have solved more of
the hardware and lifecycle problem.

### Newer experiments

`claude-thing` demonstrates that a custom HUD and host relay can be built on a
Nocturne-derived image. `carthing-apps` independently documents on-device voice
memo capture and notes two ALSA capture links (`hw:0,0` and `hw:0,1`). These are
useful validation, not better foundations than Mira/Nocturne.

## Microphone answer

### Can we access it usefully?

Yes. Confidence is high.

Mira's pipeline is `mic -> wake/endpoint -> sherpa ASR -> resolver`, with the
wake and ASR sources public. DeskThing separately documents raw audio delivery
to an app callback. This establishes both driver access and application-level
capture. The Car Thing was designed around a four-microphone array, though the
available APIs may expose an already mixed/processed mono capture rather than
four independent raw channels. Phase 2 must enumerate ALSA devices and formats
to answer that last detail.

### Can it stream to the host at conversational latency?

Almost certainly. 16 kHz mono S16LE is only 32 KB/s. Even 20 ms packets are 640
bytes before framing. USB Ethernet has orders of magnitude more bandwidth. The
latency risk is software buffering: DeskThing's documented example uses
one-second chunks, which is too coarse for barge-in but configurable. The bridge
should send 20–40 ms PCM frames (or 100 ms initially), use a bounded jitter
buffer, and never write raw audio to disk by default.

First benchmark end-to-end packet age, loss, and CPU utilization. Opus is not
needed over USB unless Bluetooth becomes the transport.

### Can Mira voice be reused for arbitrary speech?

Partly. Its capture, wake model, endpointing, and sherpa ASR are generic enough
to reuse. Its post-ASR intent grammar, library phonetic re-ranking, and action
dispatcher are Spotify-specific and should not sit in front of Muse. For best
latency, keep only wake/VAD on-device in ambient mode and stream conversation
audio to host STT. Mira's small ASR can remain an offline/fallback option.

## Proposed architecture

```text
Car Thing (Mira-derived thin client)
  hardware input + touchscreen
  UI state renderer
  mic controller + local wake/VAD + short RAM pre-roll
  audio/event bridge
             |
             | USB Ethernet; versioned WebSocket + binary PCM
             v
Omarchy host gateway
  authoritative mic/session state machine
  dashboard state aggregator
  streaming STT adapter
  Muse adapter (conversation/session ID retained here)
  Spotify / calendar / weather / reminders
  streaming TTS -> PipeWire shed speakers
```

The UI and Muse never call one another directly. The host gateway translates
Muse/tool activity into a generic appliance protocol.

### Protocol sketch (`muse-thing/1`)

Control messages are JSON over one authenticated local WebSocket. Audio frames
are binary on the same socket initially; move to a second socket only if
head-of-line blocking is observed. Every message has `v`, `type`, `id`, and
`ts`; state updates also carry a monotonically increasing `revision`.

Host -> device message types:

- `dashboard_state` — clock formatting, active card ordering, connectivity
- `now_playing` — title, artist, artwork URL/hash, duration, position, state
- `next_event` — title, start, relative label; private-title redaction flag
- `weather` — temperature, condition, icon, optional short forecast
- `listening_state` — `off | ambient | listening | thinking | speaking`
- `transcript` — partial/final user transcript, short display form
- `assistant_response` — short display form plus speech status
- `choice`, `approval`, `notification` — generic interactive cards

Device -> host message types:

- `hello` / `capabilities`
- `input` — semantic action plus physical source and press phase
- `mic_state_request` — requested privacy state transition
- `wake_detected`, `speech_start`, `speech_end`
- `audio_start`, binary audio frames, `audio_end`
- `ui_action`, `ack`, `health`

The device renders the last complete state through a host restart. Commands are
idempotent by `id`; approvals expire; reconnects request a full snapshot.

## Interaction recommendation

- Knob turn: system/shed volume on normal screens; selection only when a choice
  overlay visibly owns focus.
- Knob press: enter conversation immediately; while listening, end utterance;
  while speaking, interrupt; long press exits the conversation session.
- Preset 1: Home.
- Preset 2: Now playing.
- Preset 3: Today.
- Preset 4: cycle `OFF -> AMBIENT -> CONVERSATION`, with a deliberate hold
  required to leave OFF. This makes accidental re-enabling harder.
- Back: cancel/dismiss; during listening or speaking, stop the current turn but
  leave the conversation session open.

Always reserve a fixed screen region for a text + icon mic indicator. Do not
encode privacy state by color alone. `OFF` should be visually dominant and
should close the capture device, stop the capture process, clear RAM pre-roll,
and cause the host to reject audio frames.

## Privacy state machine

- **OFF:** ALSA capture closed; no wake/VAD/STT; buffers zeroed; red persistent
  `MIC OFF` indicator. Host treats unexpected audio as a fault.
- **AMBIENT:** on-device wake/VAD only; rolling pre-roll in RAM; no continuous
  room audio transmitted. On wake, transition visibly before streaming.
- **CONVERSATION:** utterances stream to the host; session stays open for a
  configurable interval (start with 3 minutes); follow-ups use VAD without a
  wake word; visible `LISTENING`, `THINKING`, and `SPEAKING` substates.

Keep the privacy state authoritative in both places and fail closed: if the
host/device states disagree or the link drops, close capture and show OFF (or a
distinct fault state), never silently remain listening.

## STT/TTS approach

Do not choose a final engine before measuring. Start with a streaming host STT
adapter and benchmark time-to-first-partial and final-transcript latency using
real shed noise. This i5 with 15 GiB can run small quantized Whisper-family or
sherpa/faster-whisper models, but cloud streaming may be more natural on older
CPU hardware. Keep the adapter interchangeable.

VAD and wake should remain local to the Car Thing. TTS should stream through
the host's PipeWire output. Support cancellation so knob press or detected
barge-in immediately stops playback.

## Physical microphone kill feasibility

Feasible in principle, unproven at board level. A genuine kill switch would
interrupt the microphone array's supply/clock/data path or assert a hardware
mute recognized below userspace. Because the device has multiple microphones,
cutting individual signal traces is unattractive; switching a shared mic-bias or
digital-mic supply would be preferable if the schematic/board measurements
confirm one.

No reliable published modification guide or verified switch point was found in
this research. Opening the unit, tracing rails, and soldering are deferred.
Software OFF is therefore the Phase 2 mechanism, clearly described as software
privacy rather than a physical guarantee. A future hardware investigation
should obtain teardown photos/schematics, identify the codec/mic parts, measure
the shared rail, and ensure switching it cannot back-power or damage the SoC.

## Smallest Phase 2 experiment

Goal: prove all risky hardware assumptions before application work.

1. Connect the Car Thing normally with a known data-capable USB cable. Record
   `lsusb`, kernel log, network interfaces, and its current screen/firmware.
2. Enter burn mode (hold presets 1+4 while connecting) only long enough to
   confirm enumeration; do not write flash yet.
3. Choose and download a pinned Mira development/release image plus a compatible
   recovery image. Record hashes. Prefer a readback/backup if the connected
   firmware/tool supports it.
4. After explicit approval, flash the pinned image using the documented tool.
5. Over the USB network/SSH, replace only the kiosk URL/app with a hello-world
   page that changes color/text for touch, knob turn/press, preset buttons, and
   back. Log raw and semantic events on the host.
6. Enumerate ALSA capture devices, record five seconds to RAM, stream 16 kHz
   mono PCM to the host, play it once through the shed speakers, then delete it.
   Measure packet/frame latency and confirm closing capture really releases the
   device.

Success criteria: custom pixels, every intended control, intelligible mic audio,
sub-200 ms steady-state audio-frame arrival, and a demonstrated OFF state that
opens no capture device. Stop there for review before dashboard work.

## Known unknowns for the physical device

- Current firmware/partition layout and whether a clean readback is available.
- Exact ALSA topology: mixed beamformed mono vs independently addressable mics.
- Whether Mira's current image exposes SSH/debug access by default.
- Real capture quality and echo behavior with the shed speakers.
- Muse's local integration/API and how it represents conversation continuity,
  approvals, tool calls, and cancellation.
- Spotify account/playback topology and calendar/weather providers.
